네, 말씀해주신 내용을 바탕으로 AI 여행 플래너 챗봇/콜봇 시스템의 흐름 정의서를 작성했습니다. 특히 팀원분들이 궁금해하시는 RAG 및 LangChain 적용 부분을 명확히 하여 이해를 돕도록 구성했습니다.

## AI 여행 플래너 시스템 흐름 정의서

### 1\. 시스템 개요

본 문서는 'AI 여행 플래너 챗봇/콜봇' 시스템의 전체적인 데이터 및 서비스 흐름을 정의합니다. 본 시스템은 사용자와의 대화를 통해 수집된 정보를 바탕으로 **RAG(Retrieval-Augmented Generation, 검색 증강 생성)** 기술을 활용하여 최적의 여행 계획을 생성하고 제안하는 것을 목표로 합니다.

### 2\. 시스템 구성 요소

| 구성 요소 | 기술 스택 | 주요 역할 |
| :--- | :--- | :--- |
| **사용자 상호작용 서버** | Java Spring Boot | • 사용자와의 직접적인 통신 (채팅 UI 응답)\<br\>• Python AI 서버와의 API 연동 및 데이터 중계 |
| **AI 기능 서버** | Python FastAPI | • 자연어 이해 (키워드 추출)\<br\>• Vector DB 검색 및 RDB 데이터 요청\<br\>• LLM을 이용한 여행 계획 생성 (RAG 파이프라인 실행) |
| **관계형 데이터베이스** | MySQL (RDB) | • 여행지, 숙소, 맛집 등 핵심 엔티티의 원본 데이터 저장\<br\>• 각 데이터는 고유한 **PK(Primary Key)** 로 관리 |
| **벡터 데이터베이스** | Chroma (Vector DB) | • RDB에 저장된 핵심 엔티티의 **설명/키워드를 임베딩한 벡터 값**과 **PK**를 쌍으로 저장\<br\>• 의미 기반 유사도 검색 담당 |
| **거대 언어 모델** | LLM (e.g., GPT, Gemini) | • **증강된 프롬프트**를 바탕으로 최종 여행 계획 텍스트 생성 |

### 3\. 정상 흐름 (Normal Flow)

사용자가 여행 계획 요청부터 응답을 받기까지의 과정은 다음과 같습니다.

1.  **[사용자] 질문에 답변**

    * 사용자는 챗봇/콜봇 화면의 질문에 대한 답변을 텍스트로 입력합니다.

2.  **[Java 서버] 사용자 답변 수신 및 전달**

    * 사용자의 답변 원문을 수신합니다.
    * 수신한 텍스트를 Python 서버 API 규약에 맞춰 그대로 전달합니다.

3.  **[Python 서버] 키워드 추출 및 벡터화**

    * 전달받은 사용자 답변에서 핵심 **키워드를 추출**합니다.
    * 추출된 키워드를 임베딩 모델을 통해 **벡터(Vector)로 변환**합니다.

4.  **[Python 서버 & Chroma DB] 유사도 검색 및 PK 획득**

    * 변환된 벡터를 사용해 **Chroma DB**에서 의미적으로 가장 유사한 데이터의 **PK 목록**을 검색합니다.
    * 이 과정이 **RAG의 '검색(Retrieval)'** 단계의 시작입니다.

5.  **[Python 서버 -\> Java 서버] PK 목록 전달**

    * 검색 결과로 얻은 PK 목록을 REST API를 통해 Java 서버로 전달합니다.

6.  **[Java 서버 & MySQL] 원본 데이터 조회**

    * 전달받은 PK 목록을 활용하여 MySQL(RDB)에서 `WHERE pk IN (...)` 쿼리를 실행합니다.
    * PK에 해당하는 여행지, 숙소 등의 **상세하고 정확한 원본 데이터를 조회**합니다.

7.  **[Java 서버 -\> Python 서버] 조회된 데이터 전달**

    * RDB에서 조회된 상세 정보를 다시 Python 서버로 전달합니다. 이로써 LLM에게 제공할 **'신뢰할 수 있는 외부 지식'** 준비가 완료됩니다.

8.  **[Python 서버 & LLM] 프롬프트 증강 및 여행 계획 생성 (RAG의 핵심)**

    * Python 서버는 \*\*(A) 7번에서 전달받은 정확한 데이터(Context)\*\*와 \*\*(B) 사용자의 최초 요청사항(Query)\*\*을 조합하여 LLM에게 전달할 \*\*'증강된 프롬프트(Augmented Prompt)'\*\*를 생성합니다.
    * LLM은 이 풍부하고 정확한 정보를 바탕으로 환각(Hallucination) 없이 \*\*실제 데이터에 기반한 여행 계획을 생성(Generation)\*\*합니다.

9.  **[Python 서버 -\> Java 서버] 생성된 여행 계획 전달**

    * LLM이 생성한 여행 계획 텍스트를 Java 서버로 반환합니다.

10. **[Java 서버 -\> 사용자] 최종 응답**

    * Java 서버는 최종적으로 생성된 여행 계획을 사용자 화면에 표시합니다.

### 4\. RAG 및 LangChain 적용 상세 설명

팀원들의 이해를 돕기 위해 RAG와 LangChain이 우리 시스템의 어느 부분에 어떻게 적용되는지 구체적으로 설명합니다.

#### **RAG (검색 증강 생성)란?**

LLM이 가진 내부 지식에만 의존하지 않고, \*\*외부 데이터베이스에서 관련 정보를 실시간으로 검색(Retrieval)\*\*하여 이를 바탕으로 \*\*답변을 생성(Generation)\*\*하는 기술입니다. 이를 통해 LLM의 약점인 **환각 현상(Hallucination)을 방지**하고, **최신 정보 및 특정 도메인의 정확한 데이터에 기반**한 답변을 만들 수 있습니다.

#### **우리 프로젝트의 RAG 적용 흐름**

위 '정상 흐름'에서 **3번부터 8번까지의 과정 전체가 하나의 RAG 파이프라인**입니다.

* **1. 검색 (Retrieval)**

    * **목표:** 사용자의 모호한 요구사항("분위기 좋은 곳")을 DB가 이해할 수 있는 명확한 정보("카페A(PK:101), 레스토랑B(PK:203)")로 변환하는 과정입니다.
    * **실행 구간:**
        * `(흐름 3, 4)`: 사용자 답변을 벡터로 만들어 **Chroma DB**에서 유사한 정보의 **PK**를 가져옵니다.
        * `(흐름 6, 7)`: 해당 PK를 이용해 **MySQL**에서 **신뢰도 높은 원본 데이터**를 가져옵니다.

* **2. 증강 (Augmentation)**

    * **목표:** LLM에게 "그냥 여행 계획 짜줘"가 아닌, "여기 \*\*[MySQL에서 가져온 구체적인 장소 목록]\*\*을 참고해서, \*\*[사용자의 원래 요청]\*\*에 맞춰 여행 계획을 짜줘" 라고 명확하게 지시하는 과정입니다.
    * **실행 구간:**
        * `(흐름 8)`: Python 서버가 검색된 데이터(Context)와 사용자 질문(Query)을 조합하여 LLM에 전달할 최종 프롬프트를 완성합니다.

* **3. 생성 (Generation)**

    * **목표:** 잘 만들어진 프롬프트를 기반으로 LLM이 최종 결과물(여행 계획)을 만드는 과정입니다.
    * **실행 구간:**
        * `(흐름 8)`: LLM이 증강된 프롬프트를 받아 답변을 생성합니다.

#### **LangChain의 역할**

**LangChain**은 위에서 설명한 복잡한 **RAG 파이프라인을 쉽게 구축하고 실행하도록 돕는 프레임워크**입니다. 우리 시스템의 **Python 서버**에서 다음과 같은 역할을 수행합니다.

* **Orchestration (조율):** (1) 사용자 입력받기 → (2) Chroma DB에 쿼리하기 → (3) Java 서버에 PK 보내기 → (4) Java 서버에서 데이터 받기 → (5) LLM 프롬프트 조합하기 → (6) LLM 호출하기 → (7) 결과 파싱하기 등 **일련의 과정을 자연스럽게 연결하고 자동화**합니다.
* **Integrations (통합):** Chroma DB, MySQL, LLM 등 각기 다른 컴포넌트들을 직접 복잡하게 연동할 필요 없이, LangChain이 제공하는 표준 인터페이스를 통해 **쉽게 연결하고 활용**할 수 있습니다.

> **결론적으로, Python 서버는 LangChain이라는 도구를 사용하여 'RAG'라는 기술적 흐름을 구현하고 있습니다.** LangChain은 RAG 파이프라인을 구성하는 '접착제'와 같은 역할을 합니다.
